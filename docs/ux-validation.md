# 配布物ごとにIMEの操作結果を記録する

この手順は、azooKey Treeの配布を判断する担当者向けです。配布候補の導入方法は[VMテスト](vm-testing.md)を参照してください。以下の「記録を作る」と「合格の条件」を先に読み、操作の確認と応答時間の測定は試験時に使います。

**自動テスト、デスクトップでの実入力、読み上げの結果は分けて記録します。** Docker/Xvfbの成功をGNOME WaylandやOrcaの確認済み範囲へ広げません。macOSのビルドはGitHub Actionsで実行できますが、実入力・候補クリック後の追加入力・VoiceOverはAppleハードウェアで確認します。

## 記録を作る

`Tools/ux-validation.py`は配布物、ソースのコミット、変換バックエンドをひとつの台帳に結び付けます。Python標準ライブラリだけで動作し、VMやコンテナを起動したり、パッケージを導入したりしません。

配布物のファイルを指定して台帳を作ります。`--commit`には、その配布物をビルドした40桁のコミットを渡してください。検証中のソースと配布物が違う場合、作業場所の`HEAD`をそのまま使わないでください。

```sh
python3 Tools/ux-validation.py init build/ux-validation/ubuntu.json \
  --artifact build/dist/azookey-tree_0.1.3_amd64.deb \
  --commit "$AZOOKEY_BUILD_COMMIT" --version tree-v0.1.3 \
  --platform ubuntu --architecture amd64 --backend cpu \
  --environment-template build/ux-validation/ubuntu-env.json
python3 Tools/ux-validation.py summary build/ux-validation/ubuntu.json
```

上の版番号は使用例です。実際に用意した配布候補の版・ファイル名へ置き換えます。通常辞書だけを使う試験は`dictionary`、ZenzaiのCPU版は`cpu`、macOSのMetal版は`metal`として台帳を分けます。モデルがロードできず通常辞書へ戻った結果を、Zenzaiの成功として記録しません。

新しい台帳の各項目はすべて未検証です。UbuntuはGTK・Qt・ChromiumとX11・GNOME Wayland、macOSはTextEdit・Safari・Chromiumを対象とします。CPU版とMetal版、amd64とarm64、表示倍率100・150・200%の結果を流用しません。ツリー表示のON/OFFと候補文字の標準/大きい設定も別々に記録します。

## 実行した組合せだけを記録する

生成された環境ファイルには配布物のSHA256、コミット、版、OS種別、アーキテクチャ、バックエンドが入ります。空欄のOS・アプリ版などを実際の値で埋めてください。台帳は証跡の内容を読んで合否を自動判断するものではありません。操作結果を見た担当者が`--status`を選びます。

| 環境ファイルの項目 | 記入内容 |
| --- | --- |
| `os_version` | ゲストを含む検証OSの実際の版 |
| `session`、`session_version` | Ubuntuは`x11`と`Xorg 21.1.11`のような実際の版、または`gnome-wayland`と`GNOME 46.0`のような版。macOSは`aqua`と対象OSの版 |
| `execution`、`hardware`、`hardware_vendor` | `vm`・`physical`・`apple-vm`、CPU/メモリなど比較に必要な構成、製造元。macOSはAppleハードウェアで確認します。 |
| `app`、`app_name`、`app_version` | 分類と実際のアプリ名・版。Ubuntuは`gtk`・`qt`・`chromium`、macOSは`textedit`・`safari`・`chromium` |
| `scale`、`tree_candidates`、`candidate_size` | 表示倍率100/150/200、ツリー表示の真偽値、候補文字の`standard`/`large` |
| `screen_reader`、`screen_reader_version` | 読み上げ試験で使ったOrca/VoiceOverとその版 |

例えば、Ubuntu X11のGTKアプリ・100%表示で入力操作を試験した結果は次のように記録します。合格を記録する前に、環境ファイルとログがその試験のものか確認してください。

```sh
python3 Tools/ux-validation.py record build/ux-validation/ubuntu.json \
  --case x11/gtk/100/tree-on/standard/composition --status pass \
  --environment build/ux-validation/ubuntu-env.json \
  --evidence build/ux-validation/gtk-composition.log \
  --note 'ツリー表示ON・文字標準で、ライブ変換ON/OFF、範囲変更、部分確定後の追加入力を確認'
```

`--evidence`は複数指定できます。ログに加えて画像や録画を添える場合も、認証画面や個人の本文が入っていないものを選びます。CLIは指定したファイルの場所・サイズ・SHA256を記録します。外部へアップロードしません。

同じ項目へ再記録すると最新の結果に置き換わります。修正前の結果も残す場合は、台帳と証跡を別に保管してください。同じ台帳への同時更新は直列に処理します。台帳と同じ場所に作られる`.lock`ファイルは排他用なので、実行中に削除しないでください。

項目IDは`表示方式/アプリ/倍率/ツリー表示/文字サイズ/操作`です。macOSの表示方式は`physical`または`apple-vm`です。ツリー表示は`tree-on`/`tree-off`、文字サイズは`standard`/`large`を指定します。操作の名前は`composition`、`pointer`、`cancel`、`focus`、`reconversion`、`dictionary`、`recovery`、`privacy`、`accessibility`、`appearance`、`latency`で、以下の試験に対応します。

## 固定の文で操作を確かめる

個人の文書・辞書・APIキーは使わず、専用ユーザーと試験用データで確認します。候補は変換器が返した実在候補を選び、選択した候補と確定結果が一致したかを記録します。

| 操作 | 手順と判定 |
| --- | --- |
| 入力・途中訂正・部分確定 | `nihongowobenkyou`を入力し、左右移動と削除・追加入力、Shift+左右、候補選択、Enter、追加入力を順に確認します。部分確定後の読みが残り、重複して確定されないことを確かめます。ライブ変換とツリー表示のON/OFFを分けます。 |
| 取消と文字種変換 | 文節を縮めてEscape→Enter、Escape→追加入力を試します。後半が消えないこと、F9/F10が選択範囲だけを確定することを確かめます。`nihongo`、`kanta`、`kitte`で「ん」「っ」を含む境界も確認します。 |
| 候補クリックと追加入力 | 「日本語」を選び、候補の語または番号をクリックしてから`a`を入力します。元の欄に「日本語あ」が一度だけ入り、入力フォーカスが残ることを確かめます。候補更新中の押下・解放、連続クリックも試します。 |
| 入力欄の切替 | 欄Aで変換を待つ間に欄Bへ移動します。Aの応答がBへ挿入されず、Aの受付済み文字も失われないことを確かめます。英数の`a→Left→b`、未確定文字への`Ctrl+h`も含めます。 |
| 確定取消・再変換 | 固定文を確定後に取り消し、再確定します。既にある文を選択して通常辞書で再変換し、選択外の文字が残ることを確かめます。未実装なら不合格または未検証として残します。 |
| 辞書の保存と復旧 | 試験専用語を追加し、保存・取消・再起動後の変換を確認します。保存失敗と不正な読みも試し、元の辞書が残ることを確かめます。設定JSONの破損試験はUbuntuの専用設定だけに行います。 |
| 遅延・停止・AI失敗 | 専用の模擬変換器で250ms、2秒、無応答、異常終了を試します。順序・取消・復旧後の入力を確認します。AIは空配列・失敗・逆順応答のmockを使い、外部AIへ実文書を送りません。 |
| 秘匿入力 | 通常欄からパスワード・PIN・PRIVATE属性の欄へ移り、通常欄へ戻ります。秘匿欄の内容を学習・候補・AI要求へ残さないことを確認します。録画には固定の試験文字だけを使います。 |
| 読み上げと確定 | VoiceOverまたはOrcaで候補名・読み・選択変更を確認し、activateまたはEnterで一度だけ確定して追加入力します。同表記異読、横スクロール、ツリーOFFも試します。読み上げソフトの版と操作手順を残します。 |
| 長文・絵文字・画面配置 | `A👨‍👩‍👧‍👦é日本語`と長い学習文を使い、カーソル位置・部分確定・折返し・画面端・複数画面を確認します。候補文字の標準/大きい設定と100・150・200%表示で、省略された表記・読みへキー操作でも到達できることを確かめます。 |
| 暗色・高コントラスト | 標準・暗色・高コントラストで候補を撮影し、選択経路と操作対象が色以外でも分かることを確認します。文字と背景の測定値を添え、ソースRGBの計算と画面上の測定を区別します。 |

ブラウザの固定入力欄は[ime-editor.html](../Tools/tests/ime-editor.html)、UbuntuのQt/Chromium用は[qt-editor.py](../Tools/tests/qt-editor.py)を利用できます。アプリ名だけでなく版、表示方式、OSの版、画面倍率、使った配布物を証跡に残します。複数の操作を一つのログにまとめる場合も、どの操作の合否かを追えるようにしてください。

## 応答時間は受付・表示・確定を分ける

測定時は、短文/長文、起動直後/継続使用、ライブ変換ON/OFFを分けます。入力イベントを送った単調増加時計の時刻を起点にし、次の区間を別々に記録します。

| 区間 | 終点 |
| --- | --- |
| キー受付 | 入力メソッドがキーイベントへ応答した時点 |
| 未確定文字の表示 | アプリ側が対応するpreedit更新を受け取った時点。画面描画完了を測った場合はその旨を明記します。 |
| 候補表示 | 対応する候補が表示された時点。変換器のJSON応答だけを測った場合は「変換器応答」として区別します。 |
| 確定 | アプリ側が確定文字を受け取った時点 |

各区間の試行数、p50・p95・p99、最大値、失敗件数を残します。p99は99%の試行が収まる時間ですが、少数試行では最大値に近くなります。試行数を添えずに性能の代表値として扱わないでください。

`latency`の結果を記録する場合は、`--metrics`に測定JSONを指定します。`measurement_scope`は`input-to-ui`とし、`samples`には短文/長文×起動直後/継続使用×ライブ変換ON/OFFの8条件を入れます。各条件の`text_length`は`short`/`long`、`startup`は`cold`/`warm`、`live`は真偽値、`count`は試行数です。`preedit_ms`・`candidate_ms`・`commit_ms`に、それぞれ`p50`・`p95`・`p99`をミリ秒で記録します。キー受付時間、最大値、失敗の内訳、測定方法は証跡側へ残します。

同じJSONの`fixture_sha256`には、測定に使った固定入力ファイルのSHA256を記録します。そのファイルも`--evidence`に指定してください。`measurement_method`には、測定区間の定義と計測ツールの版を記録します。基準となる版との比較では、この2項目も一致している必要があります。

変換器の応答時間だけを測った結果には、アプリ側の表示や確定までの時間が含まれません。その数値をこの測定JSONへ入れず、補助資料として残してください。値が足りない場合は未検証のままにします。

基準値は初回の実測から決めます。未測定の目標値や退行の許容幅を合格条件として作りません。後の版と比較するときは、マシン、OS・アプリ版、バックエンド、表示倍率、ライブ変換、入力文、測定区間を揃えます。VMの値から実機の速度を判断しません。同じ文の再入力にはキャッシュが効くため、別の固定文も含めて測定します。

## 合格の条件

| 状態 | 記録する内容 | 配布判断 |
| --- | --- | --- |
| 合格 | 実行条件と操作結果、実在する証跡 | その組合せについて確認済みです。 |
| 不合格 | 期待値と実測値、再現手順 | 修正後に同じ操作を再検証します。 |
| 未検証 | 未実施の理由と次の確認先 | 完了として扱いません。 |
| 非対応 | サポート対象外である理由 | 合格へ換算しません。対応対象との食い違いを確認します。 |

`check`で台帳、配布物、証跡の整合を確認してから判断します。配布物を作り直した場合は新しい台帳を作り、以前の合格をコピーしません。台帳の検査が通っても、実行者が記録した操作内容を第三者がレビューする必要があります。

```sh
python3 Tools/ux-validation.py check build/ux-validation/ubuntu.json \
  --artifact build/dist/azookey-tree_0.1.3_amd64.deb \
  --commit "$AZOOKEY_BUILD_COMMIT" --version tree-v0.1.3
```

検査に失敗したら、`summary`で残る項目を確認します。以前の台帳を`--baseline`へ渡すと、条件の揃った応答時間を比較できます。別コミット間の比較はできますが、環境が違う値を速度改善の根拠にしません。比較結果には自動の合格閾値を設けていません。

`check`の終了コードは、全件合格が0、未検証・不合格・非対応が残る場合が1、証跡の不整合や不正な記録がある場合が2です。

リリースノートと[対応範囲](platform-support.md)には、この台帳と同じ確認範囲・未検証項目を書きます。Appleハードウェア待ち、Orca未確認、特定アプリの不合格などを、自動テストの成功で埋めないでください。

用語は、**配布物**が導入したdeb/zip、**コミット**がその作成元、**バックエンド**が通常辞書・CPU・Metal、**証跡**が固定入力の結果を示すログ・画像・録画を指します。手順の不足や判断が分かれた項目は[検証基準のIssue #27](https://github.com/aida0710/azooKey-Desktop/issues/27)へ記録します。
