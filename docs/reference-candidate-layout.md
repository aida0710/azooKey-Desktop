# 元動画との表示比較と修正

参照は[指定された動画](https://video.twimg.com/amplify_video/2111876161710206977/vid/avc1/1920x1080/Ex9T3fPXfVVeRIbz.mp4?tag=29)です。2026-10-20に9秒付近などを見直しました。[作者の投稿](https://x.com/nya3_neko2/status/2111968066674335912)は紫をZenzaiの補正と説明しています。

0.1.0は実在する全文候補の接頭語ツリーをすべて配置し、親を子の中央へ置いていました。結果として大きな背景、広い列、縦スクロールが生じました。元動画の「選ばれた文が上段を横に伸び、各語の代替だけが下に枝分かれする」表示を再現できていませんでした。これは設計への落とし込みの誤りです。

## 開発版の変更

- 木表示が有効ならライブ変換の入力中にも表示します。0.1.0は上流の通常リストと同じ条件で隠していました。全文候補の実際の番号を保持し、入力中のクリックでも先頭文節の別候補を誤確定しないようにします。
- 選択中の実在候補を最上段の一直線に配置します。各語の同じ親を持つ代替は最大2つ表示し、下段のさらに先の枝は展開しません。
- 表示から省かれた候補も削除せず、矢印、Space、数字キーによる既存の選択を維持します。候補を切り替えると、その実在する経路が上段へ移ります。
- 語幅に合わせた小さいチップと細い曲線にします。候補領域全体は不透明にし、外周の丸角部分のみ透明です。読みはツールチップ・アクセシビリティ情報に残します。
- macOSとUbuntu GTK/GNOMEはCoreが決めた同じ列を表示します。多数の候補があっても縦方向は3段以内です。長い文は横スクロールします。
- マウスでは語を単クリックするとその経路に対応する候補を確定します。単クリックで語を移動させてからダブルクリックを待つ方式では、2回目が別の語に当たるためです。キーで経路を選び直し、Enterでも確定できます。操作対象の語を細い下線で示します。
- 番号ボタンは数字キーによる選択モードだけに表示します。通常の入力時は末尾の確定ボタンを並べません。

## 残る差

数値と青・橙の区別は下記の相対スコアとして実装しました。動画と同じ計算式だと確認したものではありません。紫とZ印によるZenzai補正の可視化と遷移アニメーションは未実装です。現在の変換APIが返す最終候補からは語ごとの補正履歴を取得できないため、Z印は付けません。

この修正は表示レイアウトの修正であり、エンジン内部の探索・補正の可視化を完成させるものではありません。元動画を完全に再現した版とは位置付けません。

実候補のトークン粒度にも依存します。VMでは「私は日本語を勉強しています」が学習後に一つの候補枠へ集約されました。隔離した学習ディレクトリでも、同じ入力の列数が初回4列から確定・再起動後1列へ変わることを確認しました。学習済みの漢字文の再解析は行っていません。全文かな・カナ候補は同じ読みの実候補に複数語の解析がある場合だけ分割し、元の確定文字列と候補番号を保ちます。長い代替で次の列をずらすことはありません。

## 語の位置・相対スコア（検証用0.1.2）

- macOSはクライアントのインライン入力のUTF-16境界座標を問い合わせ、本文の各語の直下へ列を配置します。取得できない場合や折り返し、画面端で全幅が収まらない場合は通常のコンパクト表示へ戻します。
- UbuntuのIBusはカーソル矩形しか公開しないため、入力開始位置とカーソルの移動量でPangoの文字幅を補正します。日本語一行の位置合わせを改善しますが、文書フォントが異なる英字混じりの語境界は推定です。完全な一致は保証しません。
- 語の表示は12px/ptを基本に、実測した幅で8px/ptまで縮小します。それでも収まらない長い候補は省略し、ツールチップ等に全文を残します。小さくするだけであらゆる長文を読みやすく表示できるわけではありません。
- 語の下の数値は、返却された `Candidate.value` を `exp(value - maxValue)` で重みに変換し、同じ親から分岐する候補の合計に対して0〜100へ換算した**相対スコア**です。同一の読みかつ同一の消費入力範囲のみ比較します。`composingCount` は入力数と表記数の単位があるため、実際に消費する入力数へ揃えて比較します。同じ確定文字列は最も高い値を一度だけ数えます。非表示の兄弟も分母に含めるため、表示中の数値だけで100にならない場合があります。
- 表示は整数への丸めです。選択中の語は75以上を青、75未満を橙にします。この閾値は本フォークの表示上の選択です。比較可能な評価がない語は「—」です。
- **正解する確率やZenzaiの語ごとの確率ではありません。** 上流はZenzaiによる並べ替え後に候補の評価値を再割り当てする場合もあります。取得候補が一つしかなければ100になることもあり、100が品質や正解を保証するものではありません。
- 選択用の番号はスコアとは別の段へ配置します。チップ間・スコアを含む候補領域全体を不透明にし、背後の文書が透けないようにします。

## 検証と配布

Coreで選択経路、実在候補との対応、500候補時の表示上限、相対スコアの比較範囲を検証します。AppKitでは表示の位置と大きさ、横スクロール、単クリック確定、重複候補、コントロール再利用、候補領域の不透明度と外側の丸角の透明度をテストします。`AZOOKEY_TREE_SNAPSHOT_DIR` を指定して `Tools/test-tree-ui.sh` を実行すると、実ビューの描画をPNGへ保存できます。この固定入力による画像は、入力方式としてのVM画面の検証とは区別します。

UbuntuはDocker内のXvfbで実変換器の結果をGTKへ渡し、3段以内の描画・不透明な背景・元の候補のクリック確定を検証します。0.1.0時点のGUI検証を今回の変更の検証として流用しません。

2026-10-20の検証用0.1.2では、macOS Core 69件とDesktopBridge 3件、macOSアプリ23件、単体AppKit描画16件、Docker内Swift 70件、実IBus統合検証が通過しました。Pythonは28件中、ディスプレイを必要とするGTKの3件をskipし、その3件を続くXvfb内で実行して通過しました。インストール済みUbuntu VMでもGTKの3件を通過しています。SwiftLintは違反0件、GNOME拡張はJavaScript構文チェックを通過しました。

先行する検証用0.1.1（コミット `463a303`）では、Ubuntu 24.04 arm64のX11セッションで次を確認しました。以下は0.1.1の結果であり、0.1.2の全アプリ再検証を意味しません。

- GTK Text Editor、Qt、Chromium/QtWebEngineで、実入力から選択文が上段に並び、透明背景の下段へ代替が分岐すること。
- ライブ入力中の単クリック確定、下段のカナ候補の確定、確定後に同じ入力欄へ「あ」を追加入力できること。
- QtでSpaceによる候補移動、右矢印による語の下線移動、番号クリックによる全文確定。
- インストール済みパッケージの整合性、CPUモデルの実変換、隔離D-Bus/Xvfbでの実IBus統合検証。

実画面の証跡は `build/reference-comparison/ubuntu-vm-{gtk,qt,chromium}-live.png` と確定後の画像です。これらは固定文のビュー描画ではなく、VMの入力方式を操作した画面です。検証用文書に追記し、既存の文書は残しました。

続いて検証用0.1.2を両VMへ導入し、macOS 26.5.2のSafariとUbuntu X11のGTK Text Editorで次を確認しました。

- 実入力「日本語入力の候補」で、語の色と相対スコアを表示すること。
- 候補領域の文字間・数値の背景も不透明で、背後の文書が透けないこと。
- 候補をクリックして確定した後、同じ入力欄へ「あ」を入力し、「日本語入力の候補あ」が残ること。

実画面の証跡は `build/reference-comparison/{macos,ubuntu}-vm-score-opaque.png` と `{macos,ubuntu}-vm-score-commit.png` です。既存の検証文書は残しました。macOSの署名と両VMの版番号も確認済みです。

macOS Safariではコンパクト表示へ戻り、本文の各語と候補列の位置にずれが残りました。語境界座標の単体テストは通過していますが、実アプリでの完全な位置合わせは未確認です。UbuntuもIBusのカーソル矩形に基づく推定です。長い代替候補の省略、学習済み全文の一枠表示、0/100などに偏る相対スコアも残ります。0.1.2のQt・Chromium・TextEditの再検証と、GNOME拡張の修正後の実画面確認は残っています。

Ubuntuを更新する際は、bridge、Pythonフロントエンド、GNOME拡張を同じパッケージで一緒に更新し、IBusと拡張を再起動します。新しい表示用snapshotの`columns`がない旧bridgeと混在させないでください。

0.1.0の配布物は残し、この修正は別バージョン0.1.2として配布します。CI通過とマージ後に配布用ワークフローでアーカイブを生成し、公開済みアーカイブのSHA-256を照合してからHomebrewの参照を更新します。
