# 元動画との表示比較と修正

参照は[指定された動画](https://video.twimg.com/amplify_video/2111876161710206977/vid/avc1/1920x1080/Ex9T3fPXfVVeRIbz.mp4?tag=29)です。2026-10-20に9秒付近などを見直しました。[作者の投稿](https://x.com/nya3_neko2/status/2111968066674335912)は紫をZenzaiの補正と説明しています。

0.1.0は実在する全文候補の接頭語ツリーをすべて配置し、親を子の中央へ置いていました。結果として大きな背景、広い列、縦スクロールが生じました。元動画の「選ばれた文が上段を横に伸び、各語の代替だけが下に枝分かれする」表示を再現できていませんでした。これは設計への落とし込みの誤りです。

## 開発版の変更

- 木表示が有効ならライブ変換の入力中にも表示します。0.1.0は上流の通常リストと同じ条件で隠していました。全文候補の実際の番号を保持し、入力中のクリックでも先頭文節の別候補を誤確定しないようにします。
- 選択中の実在候補を最上段の一直線に配置します。各語の同じ親を持つ代替は最大2つ表示し、下段のさらに先の枝は展開しません。
- 表示から省かれた候補も削除せず、矢印、Space、数字キーによる既存の選択を維持します。候補を切り替えると、その実在する経路が上段へ移ります。
- 語幅に合わせた小さいチップ、細い曲線、透明なウィンドウ背景にします。読みはmacOSのツールチップとアクセシビリティ情報に残し、全ノードの下には常時表示しません。
- macOSとUbuntu GTK/GNOMEはCoreが決めた同じ列を表示します。多数の候補があっても縦方向は3段以内です。長い文は横スクロールします。
- マウスでは語を単クリックするとその経路に対応する候補を確定します。単クリックで語を移動させてからダブルクリックを待つ方式では、2回目が別の語に当たるためです。キーで経路を選び直し、Enterでも確定できます。操作対象の語を細い下線で示します。
- 番号ボタンは数字キーによる選択モードだけに表示します。通常の入力時は末尾の確定ボタンを並べません。

## 残る差

動画にある数値、青と橙の区別、紫とZ印によるZenzai補正の可視化、遷移アニメーションは未実装です。現在の変換APIから受け取る最終候補だけでは、語ごとの補正履歴や動画と同じ数値の計算根拠を確認できません。候補の順位を確率へ言い換えたり、選択中の語に紫のZ印を付けたりしません。

この修正は表示レイアウトの修正であり、エンジン内部の探索・補正の可視化を完成させるものではありません。元動画を完全に再現した版とは位置付けません。

## 検証と配布

Coreで選択経路、実在候補との対応、500候補時の表示上限を検証します。AppKitでは表示の位置と大きさ、横スクロール、単クリック確定、重複候補、コントロール再利用、透明背景をテストします。`AZOOKEY_TREE_SNAPSHOT_DIR` を指定して `Tools/test-tree-ui.sh` を実行すると、実ビューの描画をPNGへ保存できます。この固定入力による画像は、入力方式としてのVM画面の検証とは区別します。

UbuntuはDocker内のXvfbで実変換器の結果をGTKへ渡し、3段以内の描画・透明背景・元の候補のクリック確定を検証します。GNOME拡張の実デスクトップ表示と両VMの画面は、修正後の再確認が必要です。0.1.0時点のGUI検証を今回の変更の検証として流用しません。

2026-10-20の修正では、macOS Core 63件、macOSアプリ18件、Docker内Core 64件、Python 20件、XvfbのGTK描画1件、実IBus統合検証が通過しました。SwiftLintは78ファイルで違反0件です。GTKテストは通常のディスプレイなしのテスト列ではskipし、続くXvfb内で必ず実行します。

Ubuntuを更新する際は、bridge、Pythonフロントエンド、GNOME拡張を同じパッケージで一緒に更新し、IBusと拡張を再起動します。新しい表示用snapshotの`columns`がない旧bridgeと混在させないでください。

公開済みの0.1.0の配布物やHomebrewの参照は、この修正を検証する途中では置き換えません。
