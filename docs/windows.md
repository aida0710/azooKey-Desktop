# Windows版（試作）

Windows 10/11 の 64 ビット（x64）と 32 ビット（x86）のアプリで使える日本語入力です。Text Services Framework（TSF）のテキストサービスとして動きます。変換はmacOS・Ubuntu版と同じCoreを使います。試作の段階で、配布物はまだありません。

## 構成

| 部品 | 役割 |
| --- | --- |
| `azookey-tsf.dll`、`x86\azookey-tsf.dll` | TSFのテキストサービス。入力欄を持つアプリごとに、そのアプリと同じビット数のものが読み込まれ、キーを受け取って未確定文字・確定・候補一覧を扱います。2つは同じ CLSID に登録します |
| `azookey-windows-host.exe` | 利用者ごとに1つ動く常駐プロセス。各アプリのテキストサービスから名前付きパイプで要求を受け、変換エンジンを1つだけ動かします |
| `azookey-settings.exe` | 設定画面とユーザー辞書の画面。常駐プロセス経由で Core の設定の操作を使います |
| `build-info.txt` | 配布物の CPU とソースのコミット（版を指定して作ったときは版も）。設定画面の診断に載せます |
| `bridge\azookey-desktop-bridge.exe` | Ubuntu版と同じ変換エンジン（Core、trait ZenzaiCPU）。Swiftの実行時ライブラリ、辞書、llama.cppのDLL（`llama.dll`・`ggml.dll`・`ggml-base.dll`・`ggml-cpu.dll`）を同じフォルダに置きます |
| `models\ggml-model-Q5_K_M.gguf` | Zenzaiのモデル（zenz-v3.2-small、Q5_K_M）。常駐プロセスがこのフォルダを`AZOOKEY_RESOURCES`としてブリッジへ渡します |
| `licenses\` | 同梱したllama.cpp（MIT、`llama.txt`）とモデル（Apache-2.0、`Apache-2.0.txt`）の告知 |

配布物は展開して約211MBです（CI run 39775273822の成果物。モデル74MB、Swiftと Visual C++ の実行時ライブラリ62MB、ブリッジ42MB、辞書29MB、llama.cppのDLL 2.3MB）。

アプリごとに変換エンジンを起動すると、辞書と学習データをアプリの数だけ読み込むため、常駐プロセスに集めています。パイプは利用者本人とSYSTEM、同じ利用者のストアアプリ（AppContainer）だけが開けます。学習データは`%LOCALAPPDATA%\azooKey Tree`に、設定ファイルは`%APPDATA%\azooKey Tree\settings.json`（場所は Core が決めます）に置きます。

## キー操作

| キー | 動作 |
| --- | --- |
| 半角/全角、Alt+`、IMEオン/オフキー | 日本語入力の切り替え |
| 無変換 / 変換 | 日本語入力を終える / 始める（Macの英数・かなと同じ）。入力中の変換キーはSpaceと同じ変換です |
| Space、↑↓ | 変換・候補の移動 |
| 1〜9 | 候補の番号で確定 |
| PageUp / PageDown | 候補のページ送り |
| Shift+←→ | 文節の伸縮 |
| F6〜F10 | ひらがな・カタカナ・全角英数・半角英数への変換 |
| Enter / Esc | 確定 / 取り消し |
| Ctrl+Shift+Backspace | 直前の確定を取り消し、変換中の状態に戻す |
| Ctrl+Shift+R | 選択した文字を再変換する |

入力中の文字は、打っている間は点線、変換中の文節は太い下線、ほかの文節は細い下線で表示します。色はアプリの配色に任せます。パスワード・PINの入力欄（InputScope）では変換を通さず、そのまま入力します。

## 確定の取り消しと再変換

直前に確定した文字を変換中に戻す（Ctrl+Shift+Backspace）ことと、選択した文字をもう一度変換する（Ctrl+Shift+R）ことができます。タスクバーの「あ」「A」を右クリックしたメニューからも選べます。何を戻せるかは Core（`ReconversionSession`）が決め、Linux・macOS と同じ条件です。

テキストサービスは、選択範囲とその前後（それぞれ256文字まで）と、文書の先頭からの位置を Core に渡します。位置は `ITfRangeACP` で読むため、文字位置を持たない入力欄では使えず、Core が理由を返します。変換を始めたときに読んだ文書の状態を変換中ずっと渡し、確定のたびにその分だけ進めます。Core は確定した文字とそのときの文書を覚え、取り消しの要求で文書が変わっていないことを確かめます。

Core が戻す文字を答えたら、一つの編集（edit session）の中で、その文字が文書のその位置にあることを確かめて消し、消した後の文書で Core に確認し、未確定の文字として置き直します。Core が断ったときは消した文字を同じ場所に戻すので、アプリには途中の状態が見えません。

漢字のように Core が読みを決められない選択は、読みの入力を求めます。カーソルの近くに「読みを入力」の表示を出し、打った読みを Enter で再変換、Esc でやめます。断られた理由（入力中の文字がある、保護された入力欄、文字が変わった など）も同じ表示で知らせ、次のキーで消します。表示はフォーカスを取らず、UI Automation の通知で読み上げソフトにも伝えます。

## AI 変換

何を送るか、送ってよいか、結果を本文へ戻してよいかは Core が決めます（[docs/ai-bridge-protocol.md](ai-bridge-protocol.md)、Linux と同じ操作）。AI への通信は、常駐プロセスが変換用とは別に起動する AI 用の変換エンジン（2 本目のブリッジ）で行うので、返事を待つ間も入力は止まりません。API キーは設定画面で資格情報マネージャーに保存し、常駐プロセスだけが読んで要求に付けます。アプリの中で動くテキストサービスには、API キーを渡しません。

- **AI 候補（Ctrl+S）**: 変換中に押すと、Core が送る内容（対象の本文、送信先のホスト、周辺テキストを含めるか）をカーソルの近くに出します。Ctrl+S で送信、Ctrl+Shift+S で周辺テキストの切り替え、Esc で取消です。ほかのキーは確認を閉じて、ふだんの入力として扱います。この窓は部品を子ウィンドウにせず自前で描くので、クリックしても文書からフォーカスを奪いません。返ってきた候補は、確認したときの変換のままなら候補一覧に並びます。
- **選択した文の変換**: 文を選んで、固定した指示のショートカット（設定で決めます）を押すと、指示画面 `azookey-ai-transform.exe` を開きます。指示を入力するか履歴から選んでプレビューし、「本文へ適用」で元の入力欄の選択を置き換えます。画面は常駐プロセスが起動します（ストアアプリのテキストサービスはプロセスを起動できないため）。選択文や周辺テキストはコマンドラインに載せず、常駐プロセスが一時トークンと引き換えに一度だけ渡します。適用は、画面を閉じて元の入力欄にフォーカスが戻ったときに、テキストサービスが選択を読み直し、Core が元の選択だと確かめた場合だけ行います。
- 何も入力していないときの Ctrl・Alt の組み合わせは、Core が返すショートカットの一覧（`ime-shortcuts`）に載っているものだけを変換エンジンへ送り、それ以外はアプリへ渡します。一覧が届く前は、Control を含むキーを Core に送ります（Core が断ればアプリへ渡します）。

## 候補の表示

何を出すかと、どこに置くかは Core が決めます（`candidateDisplay` と `candidate-layout`、[docs/candidate-display.md](candidate-display.md)）。GTK・GNOME と同じ判断です。Windows 側は文字の幅と1行の高さを測り、Core が返した枠のとおりに描きます。

打っている間は、枝分かれする木（Linux の木構造の候補表示）を未確定の文字の下に出します。語が文書の語の幅に収まるときは、列を文書の語の下にそろえます。Space で変換すると、番号付きの候補（Core の 9 件のページ）の一覧を出します。候補をクリックすると選択、ダブルクリック・「確定」・Enter で確定します（Linux と同じく、選択と確定を分けています）。‹ › でページを送ります。候補のパネルはアプリからフォーカスを奪いません。

置き場所は下・上・右・左の順に探し、入力中の行には重ねません。どの向きにも入りきらず Core が高さを縮めたときは、パネルの中身をスクロールし、選択中の候補か操作中の語が見えるようにします（ホイールでも動かせます）。

描画は Direct2D で、モニターごとの表示倍率と、Windows の「テキストのサイズ」の設定に合わせます。パネルは層ウィンドウ（`WS_EX_LAYERED`）で、Direct2D でメモリー上の画像に描き、`UpdateLayeredWindow` で位置・大きさ・中身を一度に替えます。木から一覧へ大きくなるときも、新しい大きさの枠に古い絵が出るコマはありません（`ID2D1HwndRenderTarget` で描いていたときは、窓を大きくしてから描き直すので1コマ出ていました）。画素ごとに透明度を持つ窓はシステムが角を丸めないので、角丸（8 DIP）と、Windows 11 の小さな窓のような下に落ちる薄い影は自前で描きます。影は「ウィンドウの下に影を表示する」の設定に従い、影の上のクリックは下の窓に通します。文字は不透明な背景の上だけに描くので、システムの ClearType の設定のまま描きます。配色は `Shared/CandidatePalettes.json` から生成した明・暗・高コントラスト（明・暗）の4種類で、Windows のアプリの配色と高コントラストの設定に従います。選択中の候補は、背景・枠・文字の色をそろえて示し、色だけに頼りません。スコアのバッジの色は Core の区分（`scorePresentation.role`）で決めます。

全画面のゲームなど、候補を自分で描くアプリ（TSF の UI-less モード）には、候補一覧を `ITfCandidateListUIElementBehavior` として渡し、IME の候補パネルは出しません。

## Zenzai（ニューラル変換）

macOS・Ubuntu版と同じZenzaiを、CPUだけで動かします。ブリッジは`AZOOKEY_RESOURCES`のフォルダにモデルがあればZenzaiを使い、無ければ辞書だけで変換します。配布物にはモデルを入れてあるので、導入すれば常に有効です（切り替える設定はまだありません）。モデルは最初の変換のときに読み込み、読み込めたかは応答の`zenzaiLoaded`に出ます。

| 項目 | 内容 |
| --- | --- |
| llama.cpp | [azooKey/llama.cpp](https://github.com/azooKey/llama.cpp)のb4846（`10131b23ee0dbd9d03dfc618cec9fe3402919277`）。上流のmacOS版の`llama.xcframework`、Ubuntu版のパッケージと同じリビジョンです。`Windows\scripts\build-llama.ps1`が取得したコミットを照合し、MSVCとNinjaでCPU用の共有ライブラリ（DLL 4つ、計約2.3MB）として作ります |
| 命令セット | `GGML_NATIVE=OFF`で、作る機械に関係なくAVX2・BMI2（MSVCではFMA・F16Cも）に固定します（Ubuntu版と同じ）。AVX2の無いCPUでの動作は、Zenzaiを使わない変換も含めて確かめていません |
| 並列 | OpenMPは使わず、ggml自身のスレッドで推論します。スレッド数は変換エンジンが論理CPU数から決め、8論理CPUなら6、4論理CPUなら3です |
| モデル | `ggml-model-Q5_K_M.gguf`（73,871,936バイト、SHA-256 `29c223d4c23327b80fd13ebb5ab2555057a46317997d5da391584ffbef0db673`）。取得元とハッシュはmacOS・Ubuntu版と同じで、`Tools\fetch-models.py --model gguf`が照合します |
| ブリッジへの渡し方 | 変換エンジン（AzooKeyKanaKanjiConverter）はWindowsでllama.cppを`systemLibrary`として扱い、自分の持つヘッダーで`llama.lib`をリンクします。CPUデバイスの取得に`ggml.lib`も要るので、`swift build --traits ZenzaiCPU -Xswiftc -L<llama.cppのlib> -Xswiftc -lggml`でビルドします。変換エンジンのヘッダーはb4846よりわずかに古い版ですが、変換エンジンが使う構造体と関数の宣言はすべて同じです（Ubuntu版も同じ組み合わせ） |

変換では、カーソルの前の文（最大100単位）と後ろの文（最大100文字）を、Zenzai に文脈として渡します（Linux・macOS と同じ）。後ろの文は、選択があればその後ろからです。例えば「kaitei」は、後ろが「に沈んだ船を調べる」なら「海底」、「された法律が施行された」なら「改定」、文脈が無ければ「書いてい」になりました（開発機のメモ帳で確認）。

使えないもの: 個人化（プロファイルの言語モデル）と誤字補正の重みは、marisa形式のファイルをWindows版の変換エンジンが読めないため使えません。

## 設定画面

`azookey-settings.exe` は、Core の設定の定義（ブリッジの操作 `settings-schema`）から画面を組み立てます。ページと項目、選択肢、既定値、文言のキーは Core が決めるので、Linux の設定画面と同じページ（入力・変換表示・辞書と学習・AI・サポート）と項目が並びます。左にページの一覧、右に選んだページの項目、下に状態の行と「保存」「キャンセル」を置きます。

開き方は、スタートメニューの「azooKey Tree の設定」と、タスクバーの入力モードの表示のメニューの「設定…」です（「ユーザー辞書…」は `--page dictionary` で「辞書と学習」のページを開きます）。設定ファイルがまだ無い最初の起動では、Linux と同じくサポートのページ（導入の案内）を開きます。画面が開いているときにもう一度起動すると、新しい画面は作らず、開いている画面を前に出して指定のページに切り替えます（最初の起動の画面がまだできていなければ、できるまで待ちます）。

| 定義の種類 | Windows の部品 |
| --- | --- |
| toggle | チェックボックス |
| choice | ドロップダウン（値は文字列・整数のまま Core へ返す） |
| integer | 数値の欄と上下の矢印 |
| text / multilineText | 1行・複数行の入力欄（カスタム入力表は複数行） |
| shortcut | 押したキーの組み合わせを記録する欄（`Ctrl+Alt+E` のように表示）。Ctrl・Alt・Shift・Windows キーのどれかが要ります。Tab・Enter・Esc は通常どおり使えます |
| dictionary | 「ユーザー辞書を編集…（N件）」ボタン |
| note | 説明文 |
| action | ボタン。学習のリセットは確認してから行います |
| secret | パスワード欄。API キーは Windows の資格情報マネージャー（汎用資格情報 `azooKey Tree/openai-compatible`、この機械だけに保存）に入れ、設定ファイルには書きません。空欄なら変更しません |
| support | サポートの欄（下記） |

- 読み込みと保存: 常駐プロセスのパイプを通して Core の操作を使い、常駐プロセスが動いていなければ起動します。要求は画面とは別のスレッドで送り、待つ間も画面は応答します。保存（`settings-save`）には開いたときの設定ファイルの版（stamp）を付けます。ほかの操作で設定ファイルが変わっていたら Core が断るので、読み直すか尋ねます（読み直すと、この画面で保存していない変更は消えます）。Core が値を断ったときは、設定項目の名前を入れた文言で知らせます（例: 推論回数が範囲外）。
- 壊れた設定ファイル: 画面の上部に理由とファイルの場所を出し、「正常な設定で復旧」「入力・表示を既定に戻して復旧」を置きます（`settings-recover`）。確認のあと、元のファイルを別名で残して置き換えます。
- Windows で使えない項目: 入力訂正、個人化モデル、入力訂正モデルのダウンロード、個人化モデルの読み込みは、変換エンジンが MARISA 形式を読めないため Core が「使えない」と返します。画面では無効にして、その下に理由を出します。
- ユーザー辞書の画面: Linux の `user_dictionary_editor.py` と同じことができます。一覧（単語・読み・ヒント・確認する内容）、単語・読み・ヒントの検索、列の見出しでの並べ替えと登録順への戻し、追加・選んだ項目の編集・削除。「保存」で Core が読みを検証し（`dictionary-validate`）、問題があれば該当する項目を選んで理由を出します。問題がなければ設定ファイルへ保存し（`dictionary-save`、stamp 付き）、変換に反映します。取込はファイルと形式（azooKey JSON、ATOK 2017 の公開テキスト、Mozc・Google 日本語入力の公開テキスト）・文字コードを選び、Core の取込内容（`dictionary-import-preview`。追加・重複・衝突・除外と理由）を確認してから下書きへ加えます。書出は下書きの全項目を azooKey JSON で書きます（`dictionary-export`）。「キャンセル」で下書きを捨てます。
- サポート: 導入と困ったときの案内、ガイド・配布版・問題の報告・上流へのリンク、設定ファイルと学習データの置き場所、Core が作る診断（版、ソース、OS、CPU、配布物の CPU、推論方式、TSF、候補の表示方式）と、そのコピー。診断には本文・辞書・指示の履歴・API キーを含めません。
- 表示: Per-Monitor V2 で、モニターの表示倍率に合わせて文字と配置を変えます。色はシステムのダイアログの配色（ハイコントラストを含む）です。すべての操作はキーボードででき、各項目には読み上げ用の名前（項目の文言）と説明を付け、状態の行の変化は読み上げソフトに伝えます。
- 文言は共通カタログ（`Shared/Messages`）から引き、Windows の UI 言語が日本語なら日本語、それ以外は英語です。

### 常駐プロセスへの反映

常駐プロセスは、各アプリの要求を変換エンジンへ渡す前に `settings.json` の大きさと最終更新時刻を見て、前に見たときと違えば `settings-reload` を送ります（Linux と同じく変わったときだけ）。設定画面で保存しても、ファイルを直接書き換えても、次の打鍵から反映します。ファイルの場所は Core の `settings-load` の応答から受け取ります。

## ビルドと導入

Visual Studio Build Tools 2022（C++のx64ツール、Windows SDK、CMake）と、Swift 6.2（`Windows\scripts\install-swift.ps1`）を使います。Zenzaiのモデルの取得にはPythonが要ります。Pythonの無い機械では、別の機械で取得・照合した`build\models\ggml-model-Q5_K_M.gguf`を写して使えます。

```powershell
# Zenzaiのモデル（git-lfsは不要。リビジョンとSHA-256を照合する）
$env:GIT_LFS_SKIP_SMUDGE = '1'
git submodule update --init azooKeyMac/Resources/gguf
python Tools\fetch-models.py --model gguf
. Windows\scripts\enter-dev-shell.ps1
Windows\scripts\build-llama.ps1
Windows\scripts\build-package.ps1 -Output build\windows-package
# 管理者のPowerShellで
build\windows-package\install.ps1
```

`build-package.ps1`は、llama.cpp（`build\llama-windows\install`）とモデル（`build\models`）が無ければ止まります。場所は`-LlamaDirectory`・`-ModelDirectory`で変えられます。`install.ps1`は`C:\Program Files\azooKey Tree`へ置き、テキストサービスを登録し、サインイン時に常駐プロセスを起動するよう設定し、日本語のキーボード一覧に追加します。Win+Spaceで切り替えられます。スタートメニュー（すべての利用者）に「azooKey Tree の設定」を置きます。`build-package.ps1`に`-Version 0.2.0`のように版を渡すと、設定画面の診断に版が出ます。削除は`uninstall.ps1`です。学習データ、設定ファイル、API キーは`-RemoveUserData`を付けたときだけ消します。

## 制約と未確認のこと

- Arm64のアプリでは使えません（x64とx86には対応）。
- Zenzaiの個人化と誤字補正の重みは使えません（marisa形式を読めないため）。Zenzaiを切る設定もまだありません。
- 常駐プロセスは起動するとすぐ、使い捨ての文脈に「nihongo」と打って Space で変換し、閉じます（暖機。確定しないので学習しません）。辞書と Zenzai の読み込みと最初の変換を、利用者が打つ前に済ませるためです。サインイン時に起動するので、普段は打ち始める前に終わっています。暖機の間に届いた変換の要求は、暖機が終わるまで待ちます。テキストサービスは常駐プロセスの応答を2秒まで待ち、それを超えるとそれまでの入力を確定して打った文字をそのまま入れます。GitHubの実行環境では、TSF の試験の最初の場面で、打鍵の途中で入力が確定されて打った文字がそのまま入ったことがあります（撮影で確認。「にほんgお」）。これはこの時間切れの形です。暖機が1文字だけだった版で起きました。どの要求が遅れたかは記録できていません。
- 常駐プロセスに `--trace <ファイル>` を付けると、変換エンジンへの要求ごとに、届いた時刻・エンジンが空くまでの待ち・処理時間を1行ずつ書きます。`tsf-cases.ps1` は自分で起動した常駐プロセスでこの記録を取り、最初の40行と1秒以上かかった要求を表示します。
- AI 変換は、実際の AI の API とアプリでは確かめていません（自動試験は模擬の API と RichEdit）。
- Core の設定の一部は、Foundation の UserDefaults として利用者の`%LOCALAPPDATA%\azookey-desktop-bridge.exe.plist`にも残ります。この機械のどのブリッジも同じファイルを使い、環境変数`LOCALAPPDATA`では移せません（確認済み）。そのため常駐プロセスを起動する試験を開発機で回すと、そのファイルが書き換わります。これが開発機での普段の入力に影響するかは確かめていません。
- 設定画面は標準のコントロールを使うため、Windowsのダークモードの配色にはなりません（ハイコントラストには従います）。
- 候補一覧のナレーターへの読み上げには未対応です。
- WindowsのSwiftは検査付き（+Asserts）の版だけが配布されており、依存ライブラリの最適化中に検査が止まるため、SIL検証を外してビルドしています（Linuxの通常版と同じ条件）。
- Smart App Controlが有効な機械では、署名のない実行ファイル・DLLが止められることがあります。開発機（Core i3-10100T）では、新しくビルドした実行ファイル（ブリッジ、試験、SwiftPMの`core-manifest.exe`）が毎回止められたため、2026-10-22 に開発機の Smart App Control を切りました。配布するにはコード署名が必要です。
- 自動試験はRichEditで行っています。メモ帳、Edge、Word、ストアアプリなどの実アプリでの入力、高DPIの複数画面、フォーカス移動時の確定は確認がまだです。
