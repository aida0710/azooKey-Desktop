# 候補の選択・確定と数字キー

候補の `1.`〜`9.` は、数字キーでその候補を確定できる状態だけに表示する。
ツリー表示 ON の候補 UI では、行・語・番号ラベルのクリックと AT activate は候補の選択だけを行う。選択後に全文と残る読みを確認し、別の確定ボタンまたは Enter で確定する。数字キーと番号ラベルのクリックは動作が異なる。

| 入力状態 | 候補番号 | 物理数字キー | ツリー ON のクリック・AT activate |
| --- | --- | --- | --- |
| 通常の候補選択 (`selecting`) | 表示 | 現在のページの実候補を直接確定 | 実候補を選択 |
| AI提案 (`replaceSuggestion`) | 非表示 | 元の読みに数字を追記 | AI提案の実候補を選択（Linux） |
| 入力中・プレビュー | 非表示 | 既存の入力処理に従う | 表示中の実候補を選択 |

候補一覧の「現在位置 / 総件数」は数字キーの割り当てとは別の情報として表示する。

ツリー ON でも、入力中に表示された候補をまだ選択していない場合、Enter は未確定文字列を確定することがある。UI が「候補のプレビュー」「この候補を確定」と表示し、Enter の印 `↵` がない状態で、Enter が表示候補を確定するとは扱わない。候補を明示的に選択すると「確定する文章」「確定 ↵」へ切り替わる。

Linux のツリー OFF は標準 IBus lookup を使う。候補行の左クリックは現在のページの実候補を直接確定し、ツリー ON のような別の確定ボタンを待たない。

Linux の GTK と GNOME Shell は `DesktopSnapshot.showCandidateIndex` を、ツリーの番号と全候補一覧の接頭辞の両方に使う。`DesktopSession.snapshot()` は `selecting` のときだけこの値を有効にする。AI提案の数字入力に対する `InputState` の動作は変更しない。

macOS の通常候補は `CandidatesViewController.showCandidateIndex`、AI提案は番号を付けない `ReplaceSuggestionsViewController` を使う。通常候補一覧も、番号の指定が空になったら行を更新して接頭辞を消す。AI専用ビューはツリーではなく、行を選択して Enter で確定する。

## 回帰試験

- Core: ライブ変換とツリー表示の各 ON/OFF で、通常の候補選択中は番号が表示され、AI提案の複数ページでは非表示になる。通常候補の物理数字キーは直接確定する。AI提案中に `1` を押すと元の読みに `1` が加わり、提案を確定しない。選択要求と確定要求を分け、同じ候補の再選択・部分候補の残る読み・古い世代の要求拒否も確認する。
- GTK: 実 Swift bridge に固定の AI提案を渡す。通常候補から切り替えると、ツリーの番号と一覧の接頭辞が消える。ページ移動後も番号を表示せず、行・語のクリックや AT activate では挿入しない。その後の確定ボタンまたは Enter で表示した提案を一度だけ確定し、元の入力欄へ続けて入力できることを確認する。通常候補の番号ラベルも選択だけを行う。
- macOS: AppKit 回帰で同じ候補の番号を表示→非表示へ切り替え、AI専用ビューの行に番号がないことを確認する。Linux の構文確認は macOS 実行結果の代わりにはならない。
- GNOME Shell: `extension.js` のツリー番号と `candidateNavigation.js` の一覧接頭辞が同じフラグで制御されることを静的確認する。実デスクトップでは AI提案を開き、番号がないこと、数字が元の読みに残ること、ページ移動後の行選択では挿入せず、別の確定操作で表示した提案を一度だけ確定することを確認する。
- Linux の標準 IBus lookup: ツリー OFF で候補行を左クリックし、その場で一度だけ確定することを確認する。ツリー ON の選択だけの動作と混同しない。

実デスクトップや VoiceOver / Orca の確認を、構文検査や GTK 部品の試験だけで完了扱いにしない。
