# 読み分離の確定取消・再変換をIBusへ接続する

開発用IBus入口では、通常入口のショートカットとメニューから確定取消・選択範囲の再変換を開始します。元の入力欄、選択本文、位置が確認できない場合や、PRIVATE指定の欄では開始しません。候補の逆引き、入力状態の復帰、文書からの削除をそれぞれ担当する側で確認します。

| 担当 | 保持する状態・処理 |
| --- | --- |
| 読みプロセス | 生入力と短期の確定履歴、削除計画、一度限りのtoken、正式な未確定入力 |
| 候補プロセス | 既存辞書による選択本文の読みの解決。候補生成や学習は行わない |
| IBus adapter | 元欄の周辺文脈、実際の削除確認、開始キーと待機中キーの元の返信 |

`undo-commit` と `reconvert` の返答は計画だけで、入力snapshotを含みません。読みに辞書が必要なら、`reconversionReadingRequest` を候補プロセスへ渡します。読みプロセスは返答の要求ID・世代・本文を照合してから計画を作ります。読みが見つからない場合は既存のローカル読み入力へ進み、Enterまで選択本文を削除しません。

adapterは削除直前にも元の文書と選択位置を照合します。`DeleteSurroundingText` を送った後、開始キーの元の返信を返し、クライアントから削除後の周辺文脈が届くのを待ちます。時間の経過を削除の成功とは扱いません。

削除が確認できた時点で、計画の原文だけを復旧用preeditに置きます。読みプロセスの返答より先にフォーカスが移っても、旧欄に原文を残すためです。この表示は元のtoken・欄・削除確認に属し、候補到着から作りません。その後の `confirm-reconversion` が正式な生入力と読みを復帰します。新しい候補batchが届いても自動選択せず、次の明示操作で選びます。古いcandidateIDや学習通知は復活させません。

正式confirmの失敗時には、その返答のsnapshotを表示しません。削除済み原文を戻せるのは、元の欄と削除後の文書がまだ一致する場合だけです。返答が不明でもconfirmを再送しません。フォーカス・本文・位置・PRIVATE属性の変更は、遅い返答と保留中の元キーを退役させます。

位置の単位は既存契約と共通です。文脈のcursor/anchorはUTF-16、IBus削除のoffset/countはUnicode scalarで渡し、本文の一致はUTF-8の列で判定します。

通常入口への切替と実アプリの受入は別に行います。特にUbuntu 24.04のQt 6.4.2では、同じInputContext内の欄移動でQt側の確定とIBus側のReset確定が重なる条件が見つかっており、共通preedit処理の修正と再検証が必要です。Pythonの状態遷移やCore試験だけでは、実アプリでの原文保持・Orca・VoiceOverの合格とは扱いません。
